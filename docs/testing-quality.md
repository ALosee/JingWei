# 测试与质量手册

Jingwei 的质量门不只是“测试通过”。它同时验证类型、风格、依赖边界、Edition 物理裁剪、生产构建和真实浏览器行为。

## 1. 根级命令

| 命令                        | 验证内容                                                            | 何时必须运行                  |
| --------------------------- | ------------------------------------------------------------------- | ----------------------------- |
| `pnpm lint`                 | ESLint 规则                                                         | TypeScript/配置变更           |
| `pnpm format:check`         | Oxfmt 排版和导入排序                                                | 手写代码、配置和文档变更      |
| `pnpm typecheck`            | 全工作区类型关系                                                    | 所有代码变更                  |
| `pnpm architecture:check`   | 模块边界、薄入口、装配、服务端分层和页面职责                        | 导入或分层变更                |
| `pnpm test`                 | Vitest 单元/集成测试                                                | 所有行为变更                  |
| `pnpm test:auth:real`       | 对已启动 Server 和真实 PostgreSQL 执行完整认证烟雾链路              | 认证、Session、CSRF、迁移变更 |
| `pnpm test:navigation:real` | 自动创建临时 PG 数据库，验证导航迁移、RBAC、租户、并发、回滚和事务  | 导航/授权/迁移变更            |
| `pnpm check`                | format:check → typecheck → lint → architecture:check → test → build | 提交前                        |
| `pnpm build`                | Edition 生成与生产打包                                              | 入口、Edition、构建变更       |
| `pnpm test:e2e`             | 浏览器端关键用户路径                                                | UI、认证、路由变更            |

`pnpm check` 已包含生产构建，但不会启动产物、运行真实 PostgreSQL suite 或 E2E；应用/构建链变更还应从纯 Node 运行构建产物，另执行相关集成测试。

## 2. 测试分层

### 2.1 领域单元测试

验证纯规则、值对象和状态转换。特点：

- 不启动 HTTP；
- 不访问数据库；
- 使用固定 `Clock`；
- 输入输出明确，运行快速。

适合覆盖依赖拓扑、权限判断、导航树算法、数据范围组合等规则。

### 2.2 应用用例测试

验证用例如何协调端口、事务、审计和事件。仓储与外部依赖可使用可观测 fake，但 fake 必须保留关键失败语义，例如唯一冲突和事务回滚。

Web 壳流程、页面 controller 与生命周期同样测试端口协作，不要求启动整个应用：导航启动测试覆盖 bootstrap/session/me 顺序、深链接与恢复；管理页测试覆盖编辑器、版本并发参数和角色授权独立状态；登录测试覆盖提交与失败；关闭测试覆盖幂等和 HTTP 先于数据库释放。

### 2.3 基础设施集成测试

使用真实 PostgreSQL 验证 SQL、约束、事务、迁移和仓储映射。以下逻辑不能只靠 mock：

- 租户过滤是否真正进入查询；
- 唯一索引和外键行为；
- outbox 的并发领取与重试；
- 会话摘要查询和过期条件；
- 迁移从旧版本升级。

### 2.4 HTTP 合约测试

通过应用实例调用真实路由，验证：

- 输入校验和状态码；
- Cookie 属性；
- 统一错误结构与 requestId；
- 未认证、无权限、CSRF 和 Origin 失败；
- 路由只在目标 Edition 中存在。

### 2.5 端到端测试

Playwright 覆盖跨前后端关键路径。目前最重要的烟雾路径包括：应用可加载、会话恢复、登录、已认证导航和退出。

本地若使用系统 Chrome：

```bash
PLAYWRIGHT_CHANNEL=chrome pnpm test:e2e
```

E2E 不应重复穷举领域规则；它验证各层组合后仍能完成用户任务。

真实认证烟雾测试要求先完成 migration、`seed:dev`、`seed:navigation` 并启动指向同一数据库的 Server。执行时通过 `TEST_ADMIN_PASSWORD` 提供开发管理员密码；测试不会打印密码或 Cookie。

Navigation 真实集成测试使用隔离临时数据库，不依赖已启动 Server；普通 pnpm test 默认跳过该 suite。需要 CREATEDB 权限及显式 DATABASE_URL（或 Node --env-file），详见 [迁移工具](../tooling/migration/README.md#testnavigationreal)。Playwright 当前四项测试使用 API mock 验证恢复/匿名刷新、分组目录、隐藏参数页面和编辑器保存/CSRF；它们不替代真实数据库测试。

## 3. 架构检查

`tooling/architecture-check` 负责把仓库约定变成可执行规则。它应至少阻止：

- 模块深层导入另一个模块的内部文件；
- platform 反向依赖业务模块；
- 模块直接依赖 app 组合根；
- 不允许的相对路径越界；
- 绕过公开入口的包路径。

当前还检查可执行入口只有 startup import/call，装配层不内联 handler/SQL，服务端依赖方向，页面不直接导入 client 或执行 fetch，以及模块不读取 process.env。完整已实现规则见 [检查器 README](../tooling/architecture-check/README.md)；不要把上述目标清单理解为任意动态代码都已被自动证明安全。

规则自身使用最小正反例测试；模块生成器用纯模板和临时目录测试验证结构且拒绝覆盖已有模块。新增语法或有意的类型端口例外必须同时加测试，不得只排除整片目录。

架构检查是护栏，不是架构设计本身。新增依赖若确实合理，先更新设计与 ADR，再精确调整规则；不要用宽泛例外关闭整类检查。

## 4. Edition 验证

Edition 既是逻辑选择，也是物理交付边界。测试应验证：

1. 根模块的传递依赖完整；
2. 循环依赖和未知模块快速失败；
3. 生成列表顺序稳定；
4. Server 和 Web 使用同一个解析结果；
5. 未选模块不会进入目标 Edition 的生成入口和生产 bundle；
6. 迁移集合与运行时模块集合一致。

仅在运行时隐藏菜单不算 Edition 测试通过。

## 5. 安全回归矩阵

身份、权限或数据访问变化至少考虑：

| 维度 | 例子                                           |
| ---- | ---------------------------------------------- |
| 身份 | 匿名、有效会话、过期会话、已撤销会话           |
| 权限 | 有权限、无权限、能力在 Edition 中不存在        |
| 租户 | 当前租户、其他租户、未知租户                   |
| CSRF | 正确 token、缺失、Cookie/头不一致、错误 Origin |
| 输入 | 正常、边界、格式错误、超长、恶意内容           |
| 并发 | 重复提交、唯一冲突、重复事件、worker 抢占      |

测试数据和快照不得包含真实密码、Token 或个人敏感信息。

## 6. 可测试性约定

- 时间依赖 `Clock`，不直接读取系统时间；
- ID 可通过工厂或 fixture 显式传入；
- 数据库行为通过端口注入，但 SQL 仍有真实集成测试；
- 路由装配可接收测试运行时；
- 日志器可替换为内存 sink；
- 事件分发器在用例测试中可记录调用，在 worker 测试中覆盖失败和重试。

`@jingwei/testing` 提供统一测试上下文和固定时钟，避免每个模块创造不兼容的 fixture 约定。

## 7. 缺陷修复标准

每次修复应先构造能够稳定复现问题的测试，再修实现。回归测试放在最接近缺陷根因的层：算法错误放单元测试，SQL 条件错误放数据库集成测试，装配错误放 HTTP/E2E。

如果问题来自架构边界未被机器检查，应同时扩展 `architecture-check`，把一次事故转化为长期护栏。

## 8. CI 建议顺序

当前 `.github/workflows/quality.yml` 在 push 和 pull request 时安装锁定依赖，并执行 `pnpm check`。格式检查不会写文件；修复方式见 [开发指南](./development-guide.md#14-lint格式化与导入排序)。真实数据库、运行产物烟雾测试和 E2E 仍按下面的变更范围另行执行，不包含在这个基础质量工作流内。

推荐流水线：

1. 安装锁定依赖；
2. 格式、lint、类型和架构检查并行；
3. 单元与普通集成测试；
4. 生成目标 Edition 并构建；
5. 启动生产 server，检查 `/health`；
6. 执行数据库迁移测试；
7. 执行 E2E；
8. 发布制品和生成物清单。

任何一步失败都不应发布同一提交的部分制品。
